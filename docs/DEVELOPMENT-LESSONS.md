# 开发经验：把用户反复指出的问题变成验收动作

最高三条原文：**Gameplay 优先；视觉、操作、剧情一致；PS3 等级视觉方向。** 不替换成新的“最高准则”。PS3 是表现方向，不等于当前样板已达到某个商业游戏。

## 任务与对白

不要再以 A 开车到 B、换地方打一组人组成章节。每个段落都要有玩家需要观察、决定和操作的事，且对局面产生可见影响。追逐要有截击和危险，护送要有人打护送对象，防守要能失守，小游戏要有任务因果。改变敌人职责、空间、环境操作和撤离方式，再决定要不要增加人数。

压缩重复路程、让下一场景从后门、货梯、地下连接自然到达；不强迫玩家原路往返接任务。安静观察、生活聊天和购物是节奏的一部分，但不能整章只有跑路与小游戏。四波有意义的护送比八波重复堆叠更合适；同样，“千人大战”不能只有远处摆设与少数小点交战。

对白先让玩家明白：为什么去、要保护谁/拿什么、谁反对、成功能改变什么。角色用完整且有语气的句子交流，幽默从关系与具体处境出来；不是越短越像真人。广告排期、账单、转运等专业词不能占据每句一半，把“谁收了谁的钱、谁在欺负谁”讲清楚。现场和电话分明，人物不抢台词、不在对话中消失。给重要演出前置因果，不靠任务卡补剧情。

## 画面与动作

用户明确说“不要乱画细条”：不要用无意义碎线、装饰格栅、地面描边和重复框线堆细节。大形体、轮廓、留白、色块、克制且有用途的结构更重要。东方明珠要有可信结构和识别度，不是随便几颗球；道路坡道接缝要实走实开，不能跳一下才上天桥。可见栏杆开口与实际碰撞相符，地面无空气墙限制车辆。

豚师必须源自第一部实际模型。不能借画风统一之名乱改头、嘴、肚子和鳍。现在选明快都市卡通，别继续把“照片写实”当未完成待办。角色手臂不能背在身后挥拳，敌人头上不能出现误用标记的大黄球；车辆转弯不能翻飞。动作质量看预备、发力、命中、受击、击退、停顿和恢复的关系，不看动画函数的数量。

重要演出需安排演员位置、视线、动作、机位、剪辑和节奏。不要让全员站木桩、相机随机绕圈；玩家在场外打败 Boss 后也必须被正确安置且不消失。友军蓝衣、原模型、黎明和情绪要一致。街头广告必须真正显示在楼上，让玩家抬头看到世界改变。

## 怎样测试才有意义

1. 先通过实际输入和物理链路验证命中、移动与碰撞，再验状态；只调用扣血函数不能证明战斗能玩。
2. 测“故意不操作”：保护对象是否真受伤、会否失败、重试是否有用。测追逐开关的时间和距离，不能只证明按钮存在。
3. 正常入口连续走与隔离测试按钮都要测。准备好的结局存档不等于完整章节衔接；剧情顺序、奖励去重和目标触发不能靠作弊跳过。
4. 读档、暂停、隐藏页面、切界面要检查敌我 HP、下注与回合、输入清理、随机状态、冷却和一次性效果，不让角色在暂停交易时继续挨打。
5. 自动检查通过后还要看原生截图和实际玩法节奏。图像显示错了，就修正重拍；不能用测试数量反驳用户的视觉反馈。
6. 明确测试证据范围。DOM/WebGL/媒体替身、headless、Linux 软件渲染、Windows 实机是不同证据；不把其中一个宣传为另一个。每轮实际截图都展示给用户，不用生成图或网页模拟图替代原生画面。
7. 必要检查通过后继续交付，不反复跑无关检查。涉及碰撞、输入、战斗和存档时做有针对性的回归；低影响文案整理不写镜像实现的测试。

## 连续工作与交接

先恢复最新源码再读交接，不根据旧临时目录猜最新版本。保存源码、依赖版本、模型来源、运行方式、验证结果、限制、下一步和用户纠正。文档不能只留最终方案，也要标清旧待办和过时说明，防止新对话重复已经修好的问题。GitHub 仓库是新对话恢复入口；只贴旧 ZIP 文件名、Library ID 或临时路径不保证新对话能取到文件。

主站、测试站、测试站2保持隔离。复制后确认内容一致再继续开发；只有用户明确要求合并/发布时才动对应站。历史交接中的“发布”“主站不动”等是当时范围，不能离开上下文执行。本轮仅迁移 Godot 工程，未修改任何 Sites。
