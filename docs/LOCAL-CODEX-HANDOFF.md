## 3. 用户真正要的游戏

最高三条保留原文：**Gameplay 优先；视觉、操作、剧情一致；PS3 等级视觉方向。**

这不是接受“能跑就算完”的原型项目。玩家需要完整空间、清楚目标、响应顺畅的操作、真实反馈、有前因后果的对白、配音和适当演出。PS3 是表现目标，不是声称当前已经达到商业游戏质量。

### 3.1 玩法、空间和战斗

- 一章不能靠开车去坐标、换位置清杂兵、拉长对白或增加敌人血量来凑时长。让路线、敌人职责、环境操作、保护对象和失败条件真正改变玩法。
- 护送对象会受伤，放任敌人确实会失败；防守目标确实能被打坏。不要用永久锁血制造“完成了护送系统”的假象。
- 允许低分继续剧情，不让蛋糕压坏、小游戏分低或竞速失利卡死主线。失败局部重试，不强迫再跑已完成的整段出游。
- 地面车辆可跨道路、人行道、广场和草地行驶，实际可见的墙、楼、柱等才挡路；不要增加空气墙或隐形车道围栏。
- 路人是同一互动世界的人，可以被拳脚和车撞伤。受伤有可读反应、倒地与合理恢复，倒地后仍是实际碰撞目标。
- 车有车况，撞击按相对接近速度、法向与方向区分正撞和擦碰；车内豚师同步受伤。顶墙踩油门不能不断重复结算撞击。上下车检查真实空间，车损和人伤要保存。
- 任务位置、距离和屏幕外方向要明确。门有实际通道和碰撞，室内有顶、有照明、有合理出入口；不能隔墙触发“进屋”。
- 每章有独立 Boss 的专属建模、动作、预兆、破绽及登场演出。借鉴《如龙》的头衔姓名卡与角色感，不是给普通敌人换名字、换颜色、加血量。

### 3.2 视觉与角色

- 明快都市卡通，参考 Bomb Rush Cyberfunk 的方向；重视大形体、色块、轮廓和留白。
- 用户反复强调“不要乱画细条”：不用密集格栅、碎线、交叉地面装饰、重复门框和无意义描边冒充细节。
- **原版豚师几何不能改。** `assets/original_dolphin.json` 是从第一部实际模型提取的，不是待重做的占位。头脸、嘴、眼睛、腹部、鳍、背鳍和比例都要保留；可适度调整材质和动画。来源还包括 `docs/original-dolphin-source.js`。
- 原版 JSON 的 SHA256 为 `7333d7666dd647f9fd858b7001bce2821705b9f6134425b0f399faacc451a08e`。不要为了通过检查改写这个基准。
- 听歌、攀哥、炫神不能照角色简笔画做成豆豆眼、椭圆嘴，也不能做尖杏眼和惊恐小瞳孔。已有圆润卡通眼、眼睑、眉、鼻、嘴和表情体系；保留各人的服装、发型和配件。
- 地面闪烁优先查共面重叠、不同地面块和悬空标线的深度冲突。移除冲突几何并在低视角移动中检查，不再盖一层贴片掩饰。

### 3.3 工作和交付偏好

- 不要每一步停下来请求确认。用户已经要求实现、修复或发布的内容，应完成到可运行、可审查、可交付。
- **当前默认不输出截图、视频或图集，除非用户明确要求。** 美术改动仍应在真实引擎中按需观察；不要为了报告额外造一轮截图。
- 新截图、视频、图集和媒体 HTML 只留在忽略的 `builds/`，不得上传仓库或 Release。用户要求看时展示真实引擎画面，不用生成图、网页模拟画面冒充。
- 减少无必要的重复检查。有关改动做有关验证；不靠反复刷测试数量取代实际体验。
- 每轮实际游戏开发结束，要提供 GitHub Release 上 Windows 可直接运行的完整 ZIP 和 SHA256。纯文档或偏好记录更新不需要新游戏版本。

## 4. 前作正史和续作开端

第一部发生在长沙。豚师从下班后回北辰处理旧帮派的麻烦出发，逐步重新面对旧朋友的劳动、旧店的责任，以及通过生意和人情控制他人的牢东杰。幽默来自熟人关系和荒诞行动，不是人人都在朗读任务指令。

第一至四章有源码快照证据，基线为 `05b4c22866a72bc6fedb3f2bdaf89e171d99e2f6`。**第五章最终源码没有恢复**；目前掌握的是用户确认的终章方向、试玩反馈和正式结局。不能把推测写成已验证的第五章关卡、最终发布版本或反派下场。

不可改的结局：问天台黎明，蓝衣朋友们归队，豚师依次宣布：

> 海豚帮解散。
>
> 海豚蒂国成立。

顺序不能颠倒。第二部已经做了这段衔接演出，再回到家中日常与八子计划，随后进入医院开场。它是为续作新制作的演出，不冒称复原了第一部最终实机录像。

八子计划是 **豚师本人在前期一胎生下八个儿子**，不是小朋友生，也不靠突然展示机器解释。八子从婴儿到长大都实际出现。故事应比第一部轻松，但不是纯旅游加随机打人；危险会打断值得玩家在乎的生活，后果也要留在生活里。

## 7. v0.8.0 第一章具体做到了哪里

连续流程是：抵沪 → 天桥竞速 → 上海中心登高及可选地标支线 → 开全家车送蛋糕 → 攀哥当面介绍象象 → 进厅认识与欢迎 → 玩家操作纸板排练 → 完整生日饭和孩子节目 → 攀哥接电话离桌 → 玩家走到真实后勤门见证交涉 → 攀哥跟车 → 工作人员遭拦截 → 护送三人撤离 → 沈铁川登场对决 → 返回生日桌、安排找攀哥。

这次扩写回应的是用户玩0.6.0后的明确反馈：不到十分钟就结束、对白像压缩摘要、运完蛋糕忽然打架、攀哥去向和人物引入缺失、没有章底 Boss。因此以后改动要同时检查**整条因果链**，不能只确认单个目标能更新。

- 八子参与出游、乘车、排戏、吃饭和章末。十座全家车容纳豚师、小朋友及八子；蛋糕急转和碰撞会受损，低分仍可推进。
- 纸板门、纸板人、软垫是实际可打的排练物件，可练破防、格挡和闪避；孩子不是伤害目标。
- 三名工作人员要真实撤到接应车。后勤门能挡增援，有实际碰撞、受阻状态和保存；清敌与撤人共同决定进展。

## 8. 天赋系统与全篇难度合同

主线、支线都给点。`assets/data/progression.json` 是预算和节点的数据入口，`TalentProgress` 是运行实现。

- 五枝：攻击、防御、体力、动作、其他；各五项，共25项。
- 各枝费用依次1、2、3、4、6，总计16；全树 **80点**。
- 全篇预留42项任务：27项主线给35点，15项支线给45点，总计80。**全任务做完才刚好点满**，不能刷怪、花钱、重玩竞速、读旧档或重开章节无限加点。
- 序章主线4点；第一章主线5点、三条地标支线各3点。连序章全做累计18，纯主线累计9。
- 目前只接入序章与第一章。后续任务预算虽存在，未制作的 `implemented=false` 项不得发奖励。
- 唯一任务 ID 的奖励账本独立于章节检查点；读档、重试、旧档补发和洗点都不得重复结算。安全时免费重配，实战中不能重配，购买和重配不回血。
- 基础格挡、闪避、三连、跳跃、破防、热血不能先收走再出售；不让付费动作成为主线硬门槛。

第二章以后，用户要求只做主线会明显难打。当前文档有建议点数、敌人倍率和测试目标，**这些尚未由后续关卡实战验证**。未来要分别实玩纯主线专攻、纯主线生存、约70%支线混合配置，用可读招式、敌人配合和资源压力形成区别，不能只堆血量，或按玩家点数暗改敌人使支线失去意义。

新增或拆分任务时同步修订账本、预算和文档，保持80点闭合；若有必要改变总量，需要有明确设计理由并同步全篇，而不是随手增发奖励。

## 10. Windows 本地第一次准备

推荐 Git、Python 3.12 和 **Godot 4.5.2 标准版**。这是 GDScript 项目，不需要 .NET、Node 或网页服务器。运行已发布 Windows 包不需要 Python；Python 用于源码工具。现有下载工具使用 Python 3.11 以上的接口，不要用过旧版本。

先在有网络时执行；下列命令使用 Windows PowerShell，命令失败应停下检查，不继续执行后续步骤：

```powershell
git clone https://github.com/Ting-777/Tunshi2_codex.git
cd Tunshi2_codex
git status --short
py -3.12 tools/restore_assets.py
py -3.12 tools/fetch_engine.py --templates
py -3.12 tools/verify_source.py
py -3.12 tools/run_native.py import --output builds/local-import
```

已克隆时不要重复克隆到已有目录。先检查本地改动与所在分支，再按实际分支关系 `git pull --ff-only`；有未提交工作或分歧时先处理，不使用强制重置和清理。`py -3.12` 不存在时，选择已安装的合适 Python，核实版本后替换命令。

两个恢复工具的区别：

- `restore_assets.py` 恢复官方 Noto 中文字体 `assets/fonts/Chinese.otf`，并按根目录 `VOICE-BUNDLE.json` 下载、校验、恢复原样配音。已有完整且匹配当前对白的缓存时跳过下载。字体 hash 不匹配就停止，不偷换另一款字体。
- `fetch_engine.py --templates` 下载并校验 Godot 4.5.2 与 Windows 运行模板等到忽略的工具目录。**它每次运行都会在线取官方校验清单，即使本地已有 ZIP，也不是纯离线检查命令。** 完成准备后，不要每次离线开工都重复运行它。

先恢复资源，再让 Godot 导入。字体、语音、引擎、模板、`.godot/`导入缓存和`builds/`产物不会随普通 Git clone 自动带下来；这是设计，不是仓库缺了一批需要重新手工上传的文件。

### 真正游玩与试听配音

用下载的 Godot 打开 `project.godot`，按 F5 运行整个工程；或在仓库根目录直接执行：

```powershell
& ".\tools\godot-4.5.2\Godot_v4.5.2-stable_win64.exe" --path .
```

已有引擎可通过 `GODOT_BIN` 或验证工具的 `--godot` 参数指定，但必须是4.5.2。**当前 `tools/run_native.py` 所有模式都追加 `--audio-driver Dummy`，包含 `run`，所以它启动时没有声音。** 测配音请用上面的正常引擎入口或编辑器，不要据此误判资源没有恢复，也不要在没试听时声称声音验收通过。

正常游玩从标题选择开始/继续序章、第一章或漫游。体验0.8.0完整新增流程，应从第一章开头重玩，不能读取旧版已经完成的章末档后认定“没有新剧情”。

### 断网前要准备什么

保留完整工作区、Git 历史、Godot可执行文件、`tools/export-templates/`、中文字体、`assets/voice/`中的MP3及清单；最好另外留一份发布语音ZIP和校验文件。需要断网安装生成工具时，在联网阶段准备相应 Python 包及全部依赖的离线缓存。纯编辑和运行既有内容不必安装 TTS 生成依赖。

`restore_assets.py` 对当前字体与完整配音缓存可以本地校验；缺少任一资源时会尝试联网。严格离线下，先从已校验的备份恢复，不能靠反复重试下载解决。改了对白之后，旧语音包不能凭空包含新录音；可以先完成字幕和演出编辑，明确记录待补配音，联网补齐后再交付完整版本。

## 11. 配音、对白与资源来源

当前固定语音资源包为 [Dolphin2-Voice-v0.8.0.zip](https://github.com/Ting-777/Tunshi2_codex/releases/download/v0.8.0/Dolphin2-Voice-v0.8.0.zip)，248句，SHA256：

```text
21592c4794942c56d9e7f2dc2e327da68f2a569f378dfe5622a557049e293dad
```

正文脚本 `docs/STORY-SCRIPT.md` 与实际 `assets/dialogue/*.json` 要同步。语音缓存按说话人和文本生成键；改台词或说话人，需要对应的新音频。不要改字幕后保留旧声音冒充完成，也不要用估计时长让口型一直张嘴。暂停、快进、跳过、读档、返回标题都应同步处理声音和口型。

用户已明确授权为本项目生成TTS上传所需对白/素材，并进一步授权 **`speech.platform.bing.com` 接收对白**。同一已授权用途不重复询问。这个授权不等于能关闭平台审核，也不扩大为任意其他目的地、任意私人文件上传。使用现有的预设合成音色，不需要克隆真人声音。

联网生成／检查命令：

```powershell
py -3.12 -m pip install edge-tts==7.3.1 mutagen==1.47.0
py -3.12 tools/generate_voice.py
py -3.12 tools/generate_voice.py --verify-only
py -3.12 tools/package_voice.py
```

生成器增量处理缺失录音，`--verify-only`不调用在线合成，但需已装本地依赖。`--replace-local`用于把活跃的旧Piper/eSpeak音频替换为当前授权的预设TTS，不是日常每次重生成的默认选项。`generate_offline_voice.py`是需另备本地依赖的机械音质备选，不是当前成品配音的来源，也不是保证开箱即用的新生成方案。

MP3 与运行 `manifest.json` 被 Git 忽略；恢复依据是跟踪的 `VOICE-BUNDLE.json`。`package_voice.py`生成新语音包、校验文件与 `builds/artifacts/voice-bundle.json`。**新包发布成功后，再把对应元数据核对后更新到根目录 `VOICE-BUNDLE.json` 并提交**，使下一次克隆能恢复新对白。不能提前固定一个尚未发布的下载地址，也不能忘记这一步让新源码仍只恢复旧语音。

Windows中文JSON和清单读写必须显式 UTF-8；本项目曾因Windows默认cp1252造成语音打包失败，已经修复，不要回退为依赖系统默认编码。工作流有语音缓存，普通台词增改不需要把几百个MP3逐个提交。

原字体、Godot及资源许可证要保留。第一部的原创歌曲《吹风》《蓝脑壳儿》《念豚师》录音未迁入本仓库；未来要用需先恢复获准原音源，不拿TTS或假音频替代后宣称原歌完成。

## 12. 验证方法：测改动，也看玩家实际经历

先按本次改动选检查。改第一章对白衔接，验证正常播放、跳过、暂停恢复、读档、人物是否在场和对应声音；改打击，走真实输入—物理—命中—受伤—倒地链路；改护送，刻意不保护一次，确认真能失败及局部重试。只直接调用扣血函数不证明打得到，只从准备好的结局档启动也不证明整章连续。

常用命令供选择，**不是要求每轮把下面每条都重复跑**：

```powershell
# 第一章专项；所有证据输出放在忽略的 builds/ 内
py -3.12 tools/run_native.py test --suite chapter1 --headless --output builds/local-chapter1

# 改到序章／开场时
py -3.12 tools/run_native.py test --suite prologue --headless --output builds/local-prologue

# 改到基础系统，按影响选专项或 full
py -3.12 tools/run_native.py test --suite impact --headless --output builds/local-impact

# 需要验证最终导出包时
py -3.12 tools/run_native.py export --output builds/local-pack
py -3.12 tools/run_native.py test --pack builds/local-pack/Dolphin2.pck --suite chapter1 --headless --output builds/local-pack-check
```

`--suite`支持`full / world / polish / vehicle / impact / prologue / chapter1`。引擎导入成功、进程退出0，都不足以说明功能通过；检查 `runtime.log` 的 `ERROR`／`SCRIPT ERROR`、实际JSON结果和退出码。包装器会检查这些，不要删掉检查迎合失败。战斗按真实物理时间运行，不用固定帧加速掩盖时序问题。

视觉修改必须在实际引擎、正常游戏距离看；无显示检查不能证明画面、配音、手感和性能好。出现失败先找原因，必要时扩大验证。已有成功的、未受本轮影响的结果可以复用。纯文档修改检查内容、链接和diff即可。

## 13. GitHub 协作与 Windows 发布

用户希望采用普通本地Git工作方式：从GitHub拉取，在本机开发，完成后推回同一仓库。保留GitHub作远端，不必把项目另行迁到云端应用或另建仓库。

```powershell
git status --short
git branch --show-current
git remote -v
git fetch origin
git log -5 --oneline
```

确认安全后再`git pull --ff-only`。若本地有改动或分支已分歧，先读diff、理解来历并保留工作；不`reset --hard`、不`clean -fdx`、不强推。提交只添加本次明确修改的文件，不把用户无关工作混进来。可按用户当前工作流使用功能分支和PR，或在已授权的main上继续；不要擅自改变分支政策。使用本机既有GitHub认证，账号令牌不进源码、日志或交接文档。

实际游戏改动完成后：

1. 更新`VERSION`、`project.godot`、`export_presets.cfg`中的相应版本信息及`docs/RELEASE-NOTES.md`；写清行为变化与限制。
2. 同步运行对白、设计文档、交接与必要的验收文字；检查原版模型未变、没有意外资源和媒体入库。

4. 完成针对性本地验证，提交并推送。main中游戏路径变化会触发`Tested Windows release`；PR验证通过不等于main已发布。
5. 等待工作流完成。失败要修复并重新验证，不交给用户一个失败的运行链接当作成品。
6. 确认Release含Windows ZIP、校验文件及对应语音包，源码提交与实际构建一致。语音新包成功发布后更新固定恢复元数据。
7. 给用户Release和可直接运行的ZIP链接，说明验证范围、实际未完成内容；文档更新不另发新游戏版本。

CI会恢复引擎和资源、增量生成语音、导出PCK，在Windows独立加载检查，再打包并运行解压后的EXE，成功才发布。当前新版本正常用`v<版本>`；已有标签会自动加build编号保留旧包，但不要依赖这个机制代替正常升版。禁止覆盖已发布的旧资产。

若本机需要打Windows包，先准备模板和有效PCK：

```powershell
py -3.12 tools/package_windows.py --pack builds/local-pack/Dolphin2.pck
$gameVersion = (Get-Content VERSION -Raw).Trim()
py -3.12 tools/verify_windows_zip.py "builds/artifacts/Dolphin2-Shanghai-Windows-v${gameVersion}.zip"
```

选择Windows ZIP时用`Dolphin2-Shanghai-Windows-*.zip`，不要拿目录里第一个任意ZIP：语音包也是ZIP。EXE与PCK必须在同一目录，用户完整解压后双击`Start.cmd`或`Dolphin2.exe`，无需另装Godot、Python或语音引擎。`Start.cmd`日志在`%LOCALAPPDATA%\Dolphin2ShanghaiToon\runtime.log`。

本地断网期间可以保留提交；恢复网络后先检查远端新增改动，再推送并等CI。没有联网发布时如实说明“本地完成，尚未发布”，不声称GitHub已有新包。

## 14. 下一轮最值得注意的事

优先响应玩家实玩反馈。当前扩写已经提交和发布，但没有独立的首次通关计时；下一次判断第一章是否足够长、足够好玩，应看完整体验与用户反馈，不拿对白句数替代结论。

继续做后续章节前，先确认第一章新流程的开饭—离席—交涉—跟车—撤离—Boss—善后是否在本机连续成立。若继续第二章，要从第一章明确交代的车辆方向、炫神同行、听歌随后会合接起，先做有意思的可玩空间和完整关键段，而不是先铺很多没有用途的上海建筑。

对白需要写得像人：有人提出需求，有人追问、反对或犹豫，角色自己作决定，再让玩家看见后果。可以有长对白和停顿；任务日志只回顾发生过的事，不能负责补写玩家没见过的情节。关心人物的生活与动机，并把这些落实到玩家愿意操作的事情上。

每轮结束留下可恢复的状态：提交、版本、已完成流程、待办、资源恢复入口、实际验证及限制。不要依赖上一段聊天、临时绝对路径或已丢失的角色图片才能继续。仓库是长期接手入口。
